HDFC Clone Behavioural Biometrics Full System Architecture

🏦 Behavioural Biometrics Architecture

Android + Desktop · 39 sensors · ML pipeline · Risk engine · HITL governance
What this system does: The HDFC Bank app clone captures 39 mobile/desktop sensor signals continuously during a banking session. These signals are processed through a feature pipeline, stored in a time-series database, and used to train a per-user behavioral model. Every subsequent session is scored in real time — if behavior deviates, the risk engine escalates (step-up auth, block, alert).
Zone 1 — Data collection
Android / Desktop app layer
39 sensors polled continuously. Raw events buffered locally. Batched every 2 seconds and sent to collection API.
Zone 2 — Feature engineering
Stream processing layer
Kafka ingests raw events. Flink computes windowed features (mean, variance, FFT, gesture shape) in real time.
Zone 3 — ML engine
Training + inference layer
Per-user LSTM/Transformer model trained on enrolled sessions. Online scoring returns risk score 0.0–1.0 per session event.
Zone 4 — Risk & governance
Decision + audit layer
Rule engine + ML score fused. Decisions: allow / step-up / block. All decisions logged to immutable audit ledger.
end-to-end flow
1
User opens HDFC clone app
Login triggers enrollment check. Sensor collection starts immediately on app launch.
2
39 sensors polled at high frequency
Accel, gyro, touch, GPS, mic, BLE, camera — all captured via platform sensor APIs.
3
Raw events → Edge buffer → Kafka
Events batched in-app. Sent via HTTPS to collection API which pushes to Kafka topic.

Flink stream processor
Computes features per 2s window. Outputs feature vector [300 floats] per user session event.
5
ML inference engine
Feature vector scored against enrolled user model. Returns risk_score + anomaly_flags.

Fuses ML score + rule engine + device trust signals → ALLOW / STEP-UP / BLOCK.
7
Response to app + audit log
Decision pushed to app via WebSocket. All events written to immutable audit ledger.
The Android app has 5 internal layers. The UI is a pixel-faithful HDFC clone. Below it, a background service runs the Sensor Abstraction Layer — invisible to the user, always collecting. Features are extracted on-device (raw sensor data never leaves the phone), then feature vectors are sent over a hardened transport to the backend.
UI Layer — HDFC clone frontend (React Native / Jetpack Compose)
Login screen
Captures typing cadence from password field. Face ID / fingerprint via BiometricPrompt.
Dashboard
Touch heatmap, scroll velocity, session time, navigation path recorded.
Transfer screen
Amount field keystroke timing, pressure, swipe-to-confirm gesture captured.
Settings / Profile
App usage pattern. Session duration. Screen orientation events.
Sensor Abstraction Layer (SAL) — runs as a background service
MotionCollector
Accel + Gyro + Rotation at 50–100 Hz via SensorEventListener. Buffers in circular array.
TouchCollector
MotionEvent hook: X/Y/pressure/size/velocity per pointer. Injected via AccessibilityService overlay.
LocationCollector
GPS (1 Hz), Wi-Fi RSSI scan (every 30s), BLE RSSI (passive), cell tower ID.
EnvCollector
Ambient light, proximity, barometer, mic energy level (no raw audio stored).
BiometricCollector
Fingerprint pass/fail events, face unlock events, PPG (heart rate) if available.
SystemCollector
Screen-on/off events, app foreground changes, battery state, charging state.
Edge Processing Layer — runs on-device (Privacy-preserving)
Feature extractor
Computes statistical features locally: mean, std-dev, FFT peaks, gesture shape descriptors. Raw sensor bytes never leave device.
Local risk scorer
Lightweight TFLite model for on-device pre-screening. Flags extreme anomalies before sending upstream.
Event buffer
SQLite ring buffer (max 10 MB). Holds last 60s of feature vectors. Retry queue for failed uploads.
Privacy filter
Strips PII (GPS coordinates → geohash precision 6, mic → energy only). Applies differential noise.
Network Transport Layer
Batch upload (HTTPS/2)
Feature vectors batched every 2s. POST /api/v1/biometric/events. JWT auth + device attestation token.
WebSocket (WSS)
Persistent connection for real-time risk decisions. Server pushes: ALLOW | STEP_UP | BLOCK.
Device attestation
Google Play Integrity API token included in every batch. Proves genuine unrooted device.
Certificate pinning
HPKP pins for API endpoints. Prevents MITM. Bypass = session blocked server-side.
Security & Compliance Layer (on-device)
TEE / Keystore
Biometric keys stored in Android Keystore (hardware-backed). Never exported to app process.
Data-at-rest encryption
AES-256-GCM for local SQLite buffer. Key in Keystore.
Root / emulator detection
Checks: SafetyNet, frida presence, Magisk, known emulator props. Locks session if detected.
Accessibility abuse guard
Detects other apps using AccessibilityService (potential keyloggers). Warns user.
This is the complete data journey — from raw sensor byte on the phone to a risk decision pushed back to the user in under 200ms.
Step 1 Sensor polling (on-device)
INPUT
39 sensor APIs at 1–200 Hz
OUTPUT
[timestamp, sensor_id, raw_vector]
Each sensor has its own polling thread. Accel/Gyro at 100 Hz. Touch events are interrupt-driven (every finger move). Location at 1 Hz. All events tagged with monotonic clock timestamp.
Step 2 On-device feature extraction (2s window)
INPUT
Raw sensor events in 2s sliding window
OUTPUT
Feature vector: ~300 floats
Window features computed: statistical (mean, std, min, max, skew, kurtosis), frequency domain (FFT top-5 peaks), gesture shape (DTW distance from template), cross-sensor correlation (accel × gyro tilt). No raw data stored beyond this point.
Step 3 Privacy transform
INPUT
Raw feature vector with location
OUTPUT
Privacy-safe feature vector
GPS → geohash-6 (±0.6km accuracy). Mic → energy band histogram (no waveform). Face → landmark distances only (no image). Differential noise ε=0.1 added to continuous features. User ID → session_token (no raw PII in transit).
Step 4 Batch upload → Kafka ingest
INPUT
HTTPS POST batch of ~60 feature vectors
OUTPUT
Kafka topic: biometric.events.raw
App batches 2s windows into 5s upload batches. Collection API validates JWT, Play Integrity token, schema, rate limits. Passes to Kafka topic partitioned by user_id. Kafka guarantees ordering per partition.
Step 5 Flink stream processing
INPUT
Kafka topic: biometric.events.raw
OUTPUT
Kafka topic: biometric.features.enriched
Apache Flink job: (1) Joins feature vectors into 30s session windows. (2) Computes session-level features: typing rhythm autocorrelation, swipe consistency score, location context stability. (3) Enriches with device trust score from device registry. Outputs enriched feature blob per session event.
Step 6 ML inference (online scoring)
INPUT
Enriched 30s session feature blob
OUTPUT
risk_score [0–1] + anomaly_flags[]
Inference service loads per-user LSTM model from model registry (Redis-cached). Runs feature blob through model → risk_score. Also runs global anomaly detector (isolation forest) for first-time-seen patterns. Publishes to Kafka topic: biometric.scores.
Step 7 Risk engine decision fusion
INPUT
ML score + rule engine + device trust
OUTPUT
Decision: ALLOW / STEP_UP / BLOCK
Combines: ML risk score (weight 0.6), rule engine (device rooted, new SIM, unusual location — weight 0.3), device trust score (weight 0.1). Thresholds: <0.3 ALLOW, 0.3–0.7 STEP_UP (OTP/fingerprint re-auth), >0.7 BLOCK + alert ops.
Step 8 Decision delivery + audit
INPUT
Risk engine decision
OUTPUT
WebSocket push to app + audit log
Decision pushed to app via persistent WebSocket connection. App enforces it (block transaction, request re-auth). Simultaneously written to immutable audit log (append-only PostgreSQL table + Kafka audit topic). Regulators can replay full session.
During the first 3–5 sessions after account creation or app install, the system is in enrollment mode. No risk scoring yet — the system is purely learning what "this user" looks like.
Session 1–5 (enrollment window)
User performs normal banking actions: login, view balance, transfer, logout. All sensor events collected with label = GENUINE.
Feature extraction & storage
Feature vectors for each 2s window stored in TimescaleDB under user_id. Tagged as enrollment_data = true.
Per-user model training
LSTM autoencoder trained on user's 5-session enrollment corpus. Input: 300-float feature vector. Output: reconstruction. High reconstruction error = anomaly.
Model artifacts stored
Trained model (.pt file) + scaler parameters + threshold calibration stored in MLflow model registry. Tagged to user_id.
Baseline profile built
Statistical baseline: per-sensor mean/std, typical session duration, usual locations (geohash), typical app navigation sequence. Stored in Redis (fast lookup) + PostgreSQL (durable).
Enrollment complete → scoring mode
After 5 sessions with sufficient data quality, user profile flagged as enrolled. Live scoring enabled. Threshold set at P99 of enrollment reconstruction error.
Every 2 seconds during a live session, the feature vector is scored. The entire path from sensor event to risk decision takes under 200ms end-to-end.
Live feature vector arrives
30s enriched session blob arrives at inference API from Flink. Format: JSON {user_id, session_id, feature_vector: [300 floats], context: {...}}.
Load user model (from Redis cache)
Model registry lookup by user_id. If cached in Redis (TTL 30min) → use cached. Else load from S3 → warm Redis. Cold load = ~50ms. Hot = ~2ms.
LSTM autoencoder inference
Feature vector passed through enrolled LSTM autoencoder. Computes reconstruction error (MSE). High error = input is unlike anything seen during enrollment.
Anomaly flag extraction
Per-sensor anomaly flags raised where individual feature dimensions exceed 3σ from enrollment baseline. e.g. flags: [TYPING_SPEED_HIGH, SWIPE_PRESSURE_UNUSUAL, LOCATION_NEW].
Risk score computation
risk_score = 0.6 × norm(reconstruction_error) + 0.25 × anomaly_flag_count/total_flags + 0.15 × context_risk_score. Clamped to [0.0, 1.0].
Decision thresholds
score < 0.30 → ALLOW (transparent). 0.30–0.55 → soft flag (log only). 0.55–0.70 → STEP_UP (silent OTP or biometric re-auth). > 0.70 → BLOCK session + ops alert.
User behavior naturally drifts — injured hand, new phone, different commute. The system must continuously update its model without being fooled by a slow-moving attacker.
Confirmed-genuine sessions
Sessions where user explicitly confirmed identity (completed OTP, biometric passed, no fraud report within 48h) are labeled CONFIRMED_GENUINE. Added to user's training corpus.
Confirmed-fraud sessions
Sessions flagged by fraud ops, user-reported, or from account takeover investigations labeled CONFIRMED_FRAUD. Used as negative examples. Never added to positive corpus.
Nightly retraining job
Scheduled Airflow DAG runs nightly per user with > 10 new confirmed-genuine sessions. Fine-tunes existing model with new data. Uses Adam optimizer, low LR (0.0001) to prevent catastrophic forgetting.
Model validation before deploy
New model evaluated on held-out validation set (last 2 enrollment sessions). Must have lower reconstruction error than current model AND pass anomaly detection smoke tests. Else: keep current model.
Gradual rollout (canary deploy)
New model served to 10% of that user's sessions for 24h. If no false-positive surge → promote to 100%. Rollback via feature flag in model registry.
Drift detection & forced re-enrollment
If global reconstruction error increases monotonically for 7 days → device/behavior change too large. User prompted for re-enrollment (5 fresh sessions). Old model archived, not deleted.
Microservices
API Gateway (Kong)
Single ingress for all API traffic. JWT validation, rate limiting, device attestation check, TLS termination. Routes to downstream microservices.
POST /biometric/events WS /session/realtime POST /auth/login GET /profile/risk-status
Collection Service (Go)
Receives sensor event batches. Validates schema and Play Integrity token. De-duplicates events by (session_id, window_ts). Writes to Kafka topic: biometric.events.raw.
Kafka producer Redis (dedup cache, TTL 60s) Prometheus metrics
Flink Stream Processor
Stateful streaming job. Keyed by user_id. Maintains 30s session window state. Computes session-level features, joins with device registry, outputs enriched feature blobs.
Kafka consumer: raw Kafka producer: enriched RocksDB (local state)
Inference Service (Python / TorchServe)
Loads per-user LSTM models from MLflow. Redis-caches hot models. Scores enriched feature blobs. Publishes risk scores. Horizontally scalable — 1 instance per 5000 active users.
Kafka consumer: enriched Redis (model cache) MLflow model registry Kafka producer: scores
Risk Engine (Python / FastAPI)
Fuses ML score with rule engine and device trust. Stateless service — all state in Redis. Publishes decisions. Triggers HITL workflows for BLOCK decisions.
Kafka consumer: scores Redis (session state) PostgreSQL (rule config) Kafka producer: decisions
Session Manager (Node.js / WebSocket)
Maintains persistent WebSocket connections to app clients. Receives decisions from Kafka, pushes to correct client WebSocket connection. Handles reconnects with exponential backoff.
Kafka consumer: decisions Redis (connection reg) WSS clients (mobile/web)
Data stores
TimescaleDB
Time-series feature vectors
Per-user feature vectors with timestamps. Hypertable partitioned by time + user_id. Retention: 90 days raw, 1 year aggregated.
PostgreSQL
User profiles, rules, audit
User enrollment status, baseline profiles, risk rule config, fraud labels. Append-only audit_log table (no UPDATE/DELETE permitted).
Redis Cluster
Hot cache + session state
Model cache (TTL 30min), session risk state, dedup keys, device trust scores. Sub-millisecond reads critical for < 200ms latency SLA.
S3 / Object Storage
Model artifacts + raw batch
MLflow model registry backend. Stores .pt model files, scaler params, training artifacts. Also stores encrypted raw event batches for compliance replay.
Kafka (MSK)
Event streaming backbone
Topics: biometric.events.raw, biometric.features.enriched, biometric.scores, biometric.decisions, audit.trail. Retention 7 days. 3× replication.
Elasticsearch
Audit search + fraud ops
Fraud analysts search session events by user, time, risk score, anomaly flags. Kibana dashboards for real-time ops monitoring.
The Desktop version (Windows/macOS) targets the HDFC NetBanking web interface. It runs as an Electron app or a browser extension. Most sensors are software-derived — no hardware sensor bus like Android. Fewer raw signals but richer keyboard and mouse behavioral data.
UI Layer — HDFC NetBanking clone (Electron / React)
Login page clone
Username field: keystroke dwell time + flight time. Password: inter-key intervals, backspace rate. These alone are strong biometrics.
Dashboard / transfers
Mouse movement trajectories, scroll wheel delta pattern, form fill order, copy-paste detection (flag for risk scoring).
Invisible overlay (for Windows)
Low-level keyboard and mouse hooks via win32 API (SetWindowsHookEx). Captures all events including mouse jitter and micro-pauses.
Browser extension mode
Chrome/Firefox extension injects content script. Captures keydown/keyup, mousemove, scroll, focus/blur events on HDFC pages only.
Sensor Abstraction Layer — Desktop equivalents of the 39 signals
Keyboard dynamics
Dwell time (key hold duration), flight time (gap between keys), digraph & trigraph latencies, error rate & correction pattern. ~8 features per keystroke.
Mouse dynamics
Velocity, acceleration, curvature, click pressure (if force trackpad), hover dwell time, scroll velocity. Bezier curve fit to movement paths.
Device motion (laptop)
Accelerometer in MacBook / some laptops via macOS CMMotionManager or Windows WinRT. Gait while typing on laptop.
Camera (WebRTC)
Webcam optional. Face presence detection (MediaPipe). Blink rate, gaze direction during high-risk transactions. Requires explicit permission.
Audio (Web Audio API)
Mic energy pattern (not raw audio). Background noise fingerprint. Keyboard click acoustics via WebAudio API at 44.1 kHz.
Network & environment
IP geolocation, Wi-Fi SSID via browser/OS API, screen resolution + DPI, OS + browser UA string, timezone, installed font list (fingerprint).
Browser fingerprint
Canvas fingerprint, WebGL renderer, AudioContext fingerprint, font list. Changes = new device. Stable per user on same machine.
Session behavior
Time of day, tab switches, idle intervals, page dwell time, back-button usage, copy-paste vs typing on amount fields.
Edge Processing — same pattern as Android, different runtime
Web Worker (browser)
Feature extraction runs in a dedicated Web Worker — off main thread, no UI jank. Computes keystroke digraph matrix, mouse path features every 2s.
Electron main process (app)
Native node.js process handles low-level hooks, buffers events in memory, signs batches with device certificate.
IndexedDB ring buffer
Last 60s of feature vectors stored in IndexedDB. Retry queue for failed uploads (same logic as Android SQLite buffer).
Privacy filter
IP → /24 subnet only. Camera → presence boolean + landmark distances only (no image). Mic → frequency histogram only.
Network transport — identical to Android
HTTPS/2 batch upload
Same Collection Service API. Feature vectors sent every 5s. Authenticated with session JWT + device certificate (stored in OS keychain).
WebSocket decision channel
Same Session Manager. Risk decisions pushed via WSS. Electron app enforces: disable transfer button, show step-up auth modal.
Device attestation
Windows: TPM 2.0 attestation via ECDSA key. macOS: Secure Enclave attestation. Browser: device certificate in OS keychain.
Certificate pinning
Electron: custom Net module with pinned certs. Browser extension: CSP + HPKP headers. Same backend validation.
Key differences vs Android (what desktop can NOT do)
No accelerometer / gyroscope (usually)
No gait data. No phone-holding angle. Only MacBook/surface tablets have motion sensors — and access is restricted on most OS.
No GPS / BLE / cellular
Location only via IP geolocation (~city level). No BLE beacon proximity. No cell tower ID. Location signal much weaker.
No hardware biometrics on same device
Windows Hello and Touch ID are available but results are opaque (pass/fail). No PPG, SpO2, iris scanner.
Richer keyboard + mouse biometrics
Desktop compensates: 50–80 keystroke features vs 5–10 on mobile touchscreen. Mouse trajectory is a stronger signal than swipe.
Every side-effecting action (transfer, beneficiary add, password change) passes through the HITL gateway. The gateway checks the current session risk score before executing. This connects directly to your Phase 7 HITL work.
Risk score → decision matrix
0.00 – 0.30
ALLOW
Transparent. Session continues. Event logged to audit trail. No user interruption.
0.30 – 0.55
SOFT FLAG
Log only. No user action. Fraud ops can see in dashboard. Used for model retraining data.
0.55 – 0.70
STEP-UP AUTH
Silent biometric re-auth (fingerprint/face). If fail → OTP to registered mobile. User sees: 'Please verify to continue'.
0.70 – 0.85
HIGH STEP-UP
Strong auth required: biometric + OTP. Maker-checker for transfers > ₹1L. Digital signature on action. Ops alerted.
0.85 – 1.00
BLOCK
Session terminated. All pending transactions cancelled. Account flagged. Ops ticket auto-created. User notified via SMS + email.
Audit trail schema (every event)
{
  event_id:        UUID v7 (monotonic),
  user_id:         SHA-256(account_number),
  session_id:      UUID v4,
  timestamp_utc:   ISO-8601 with µs precision,
  risk_score:      float [0.0 – 1.0],
  decision:        ALLOW | SOFT_FLAG | STEP_UP | BLOCK,
  anomaly_flags:   string[],
  ml_model_version: semver,
  rule_engine_version: semver,
  action_requested: { type, amount, beneficiary_hash },
  auth_factors_presented: string[],
  approver_id:     UUID | null (maker-checker),
  digital_signature: base64(ECDSA-P256),
  immutable:       true   // no UPDATE/DELETE on this table
}
Governance controls
Maker-checker
Transfers > ₹1L require a second authorized user (relationship manager or ops) to approve. Both signatures logged.
Model governance
No model deployed to production without: validation metrics pass, sign-off from ML lead, canary rollout, rollback plan in place.
Data retention
Raw feature vectors: 90 days. Audit log: 7 years (RBI mandate). Model training data: 5 years. Biometric enrollment: user-deletable (GDPR Article 17).
Explainability
Every STEP_UP / BLOCK decision accompanied by top-3 anomaly features in human-readable form. Fraud ops can read: 'Typing speed 3σ above baseline'.
False positive monitoring
If STEP_UP rate for a user exceeds 20% over 7 days → auto-flag for model review. Prevents user friction from model drift.
Right to explanation
User can request explanation of any blocked transaction. System must return: time, risk score, top anomaly reasons. No raw biometric data exposed.
